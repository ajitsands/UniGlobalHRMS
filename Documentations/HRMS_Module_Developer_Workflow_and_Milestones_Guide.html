02 6-Milestone Delivery Roadmap & Engineering Acceptance Gates (22 Weeks)

The project follows a 22-week (5.5-month / 110 working days) iterative engineering roadmap across six (6) distinct delivery milestones. Every milestone has strict verification benchmarks and an explicit Definition of Done (DoD) that developers must validate before submitting for client UAT sign-off:

Milestone 1: Core Architecture, Entity Master & Loaded Rate Schema
Weeks 1–4 (Month 1) • Deliverable Ref: D-HRMS-M1
Clean Architecture scaffold, SQL Server 2022 DB migration engine, dual authentication handler (Prompt ERP API vs. local DB), Master Employee entity schema, 5 Business Units & 4 CR data structure, Loaded Hourly Labour Rate schema (Base + Indemnity + Leave + SIO/PIFSS burden), bulk Excel importer, and Milestone 1 interactive UI/UX PoC wireframes.
Engineering Verification Gate: 100% schema validation in SQL 2022; passing unit tests for bulk spreadsheet import parsing 500+ mock records; loaded rate calculation algorithm returns verified hourly cost rates consumable by CRM & Project Tracker via REST API.
Milestone 2: Shift Engine, Biometric Hardware Sync & Attendance Processing
Weeks 5–8 (Month 2) • Deliverable Ref: D-HRMS-M2
Multi-pattern shift scheduling (rotating, split, custom off-days), automated Ramadan working hours reduction engine (statutory rules for Muslim employees under Bahrain & Kuwait laws), background TCP/IP socket daemon for direct physical biometric device synchronization, punch in/out pairing logic, manual punch regularization workflows, and penalty deductions calculator.
Engineering Verification Gate: Physical or socket-simulated biometric device test transmitting real-time punches; automated pairing logic correctly flags missing punches, tardiness, and Ramadan 6-hour caps; penalty deduction engine passes all boundary test suites.
Milestone 3: Bahrain & Kuwait Statutory Payroll Engine, Overtime & EOSB Accruals
Weeks 9–12 (Month 3) • Deliverable Ref: D-HRMS-M3
Dual-country statutory payroll calculation engine implementing Bahrain Labour Law and Kuwait Labour Law No. 6 of 2010; SIO pension deductions (Bahraini vs. Expat) and PIFSS deductions (Kuwaiti vs. Expat); Overtime calculation matrix (1.25x normal day, 1.50x rest day/holiday); monthly End-of-Service Benefit (EOSB) indemnity accrual ledger with automatic GL reversal posting on termination; Bahrain CBB WPS file generator and Kuwait CBK WPS file generator.
Engineering Verification Gate: Zero variance (0.000) mathematical reconciliation against client historical payroll runs down to the exact fils; WPS text file validation against official Central Bank specifications; automated journal entry generation for monthly EOSB provisions.
Milestone 4: Bilingual ESS/MSS Web Portals & 5 BU Overhead Apportionment
Weeks 13–16 (Month 4) • Deliverable Ref: D-HRMS-M4
Fully responsive bilingual (Arabic RTL & English LTR) Employee Self-Service (ESS) and Manager Self-Service (MSS) web portals; dynamic bilingual employee letter generator (Salary Certificate, NOC, Bank Letter) with merge fields; automated document expiry alerts (CPR, Passport, Visa, Residence, LMRA, Medical) with escalation rules; 5 Business Unit overhead cost allocation engine; sales commission payroll trigger endpoint.
Engineering Verification Gate: Full self-service lifecycle test from employee leave request to manager multi-tier approval; dynamic PDF letter generation with Arabic merge tags; verified cost distribution reports apportioning shared back-office costs across all 5 BUs.
Milestone 5: React Native Mobile Application & Security Gateway (Req 92)
Weeks 17–20 (Month 5) • Deliverable Ref: D-HRMS-M5
Production-grade cross-platform mobile application in React Native for iOS and Android implementing all 14 mandatory clauses of Requirement 92: Biometric authentication (FaceID/Fingerprint), offline SQLite punch caching with automatic synchronization upon network reconnection, GPS geofencing radius validation, ESS leave requests, mobile payslip viewer, push notifications, and administrative device authorization console with remote wipe capability.
Engineering Verification Gate: Physical APK/IPA installation on iOS and Android test devices; offline punch simulation followed by network restore auto-sync; GPS geofencing radius boundary validation (±50m tolerance); admin remote device de-authorization test.
Milestone 6: User Acceptance Testing (UAT), Parallel Live Payroll & Production Cutover
Weeks 21–22 (Month 5.5) • Deliverable Ref: D-HRMS-M6 (FINAL GO-LIVE)
End-to-end UAT verification against all 92 specifications; live parallel payroll run with client Finance and HR teams; bilingual administrative and end-user training sessions; Vulnerability Assessment & Penetration Testing (VAPT) hardening; production server deployment and Go-Live Cutover (**LIVE at Week 22**).
Engineering Verification Gate: Zero unresolved Severity 1 (Critical) or Severity 2 (Major) defects; parallel live payroll run executed with 100% reconciliation against manual finance records; formal execution of Milestone Acceptance Certificate.

04 Developer Operational Workflow, Git Strategy & Code Quality Standards

To maintain zero technical debt, ensure predictable milestone releases, and prevent merge collisions across squads, all engineers must comply with the following operational engineering protocols:

4.1 Git Branching Strategy (GitFlow Standard)
  • main: Production-only branch. Code is merged here strictly upon milestone sign-off and production release tagging (e.g. v1.0.0-M6). Direct commits are permanently disabled.
  • develop: Integration branch for continuous integration. All feature branches branch off and merge back into develop via Pull Requests (PRs).
  • feature/HRMS-{id}-{description}: Developers create isolated feature branches for each requirement (e.g. feature/HRMS-3.3.01-final-settlement). Must rebase on develop before creating a PR.
  • bugfix/HRMS-{ticket}-{description}: Created from develop for non-critical defect remediation identified during sprint testing or UAT.
  • hotfix/HRMS-{p1_ticket}: Created directly from main strictly for Severity 1 (Critical) production patches. Merged back to both main and develop immediately upon deployment.
4.2 Pull Request (PR) & Code Review Checklist

No code shall be merged into develop or main without satisfying the following mandatory gates:

Mandatory Definition of Done (DoD) Checklist
  • Peer Review: Minimum of one (1) approving review from a Senior Architect or Squad Lead.
  • Automated Unit Tests: New calculation logic (payroll, SIO, EOSB, overtime) must include unit tests with minimum 80% code coverage.
  • Static Analysis: Clean Roslyn / SonarQube scan with zero critical code smells, security vulnerabilities, or cyclic dependencies.
  • Clean Architecture Compliance: Domain entities must remain pure POCOs without database or UI dependencies; all DB queries in Application/Infrastructure layers.
  • Database Migrations: Any schema alteration must include an EF Core migration file and verified idempotent SQL rollback script.
  • Bilingual UI Validation: Every frontend string must reference translation keys (en.json & ar.json); hardcoded UI strings are rejected.
05 Customer Complaints, Grievance Redressal & Defect Severity Workflows

A high-reliability enterprise ERP deployment requires a structured, transparent, and rigorous bug-tracking and grievance redressal workflow. All defects, anomalies, and customer complaints logged by UniGlobal or Prompt ERP stakeholders during development, UAT, and post-go-live warranty must be processed through the following binding operational matrix:

5.1 Defect Severity Classification Matrix & Binding SLAs
Severity Tier Technical Definition & Operational Impact Response SLA Target Resolution SLA
Severity 1 (Critical) System Halt / Blocker: Complete system outage, database corruption, total failure of monthly payroll processing, biometric hardware sync breakdown, security breach, or any issue halting all UAT testing. Within 1 Hour 4 – 12 Hours
Continuous engineer standby
Severity 2 (Major) Major Functional Impairment: Major feature failure without a viable workaround (e.g. SIO/PIFSS calculation bug, EOSB indemnity accrual variance, REST API failure with Prompt GL, React Native mobile offline sync failure). Within 2 Hours Within 24 Hours
Severity 3 (Medium) Non-Critical Functional Defect: Minor feature anomaly where an acceptable operational workaround exists (e.g. reporting filter anomaly, UI sorting inconsistency, non-blocking notification delay). Within 4 Hours 48 – 72 Hours

Scheduled deployment cycle
5.2 End-to-End Defect Lifecycle & Resolution Workflow

Every customer complaint and defect ticket must transition through the formal 6-stage engineering lifecycle:

STAGE 1
Logging & Ticket Capture: Client or QA logs issue in the Project Management Portal with mandatory metadata: Environment (Staging/Prod), Module, Steps to Reproduce, Expected vs. Actual Result, and Screenshots/Logs.
STAGE 2
Triage & Severity Assignment: Squad Lead reviews ticket within the Response SLA, assigns formal Severity Tier (P1–P4), verifies reproducibility, and assigns to the designated module developer.
STAGE 3
Root Cause Analysis (RCA) & Patch Development: Developer isolates the root cause (Domain Rule, Stored Procedure, API, or Mobile State), develops the patch, and writes an automated regression test.
STAGE 4
Code Review & Staging QA Verification: PR is submitted, reviewed by Architect, and deployed to Staging environment. QA executes regression test suite to verify the bug is eliminated without side effects.
STAGE 5
Deployment & Client Verification: Patch is published to UAT / Production. Client is notified via formal Release Note and conducts verification within 3 business days.
STAGE 6
Post-Mortem & Ticket Closure: For all Severity 1 and Severity 2 incidents, a formal RCA Post-Mortem report is archived in the portal and ticket is transitioned to Closed status.

06 Post-Deployment Warranty, Hypercare & Infrastructure Uptime Governance

Following Milestone 6 Go-Live Cutover (Week 22), the project enters a structured 60-Day Hypercare & Warranty phase. Developers must follow these operational rules:

  • Two Live Payroll Cycles Standby: Dedicated engineering standby across the first two live monthly payroll runs to ensure flawless WPS bank transfers, SIO reconciliation, and GL posting.
  • Zero-Cost Bug Remediation: 100% free engineering remediation of any software bugs or latent calculation variances identified against the 92 requirements.
  • Rapid Hypercare Triage: Daily virtual morning standups during the initial 14 calendar days post-go-live; weekly review sessions thereafter.
Developer Note: Infrastructure Boundary & SLA Voidance Rule

Provider-Managed vs. Client-Handled Servers: The 99.5% Service Availability & Infrastructure Uptime SLA applies strictly if SaNDS Lab provides and directly manages the hosting server environment. If the server is provided, hosted, or administered by the Client, the 99.5% uptime SLA is null and void. In client-hosted environments, SaNDS Lab's responsibility is confined strictly to application software bug remediation under Section 05.
